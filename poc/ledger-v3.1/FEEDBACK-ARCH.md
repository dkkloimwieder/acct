Splitting this into what I think is structurally wrong versus what's merely expensive. The spec-level defects from before are fixable; these are load-bearing choices.

## The architectural problems

### 1. Risk inversion: the deferred half is the hard half, and it has a structural throughput problem

Path C's bet is "hot path cheap now, reconciliation later." But recalc must process **the same event volume** as the hot path while doing strictly *more* work per line (layer math, adjustment posting, materialization), sequentially per pool, while contending with a hot path that keeps appending. If the hot path needed batching heroics to keep up, the reconciler — which cannot skip anything — is harder, not easier. Its only advantages are latency-insensitivity and per-pool parallelism. The failure mode is quiet: backlog grows, provisional drift compounds, period close blocks, and the close posts an adjustment storm into the GL. SAP/Oracle/D365 being cited as precedent cuts both ways — CKMLCP and Inventory Close are famously the *worst-behaved* components of those systems (multi-hour closes, locking entire plants). The PoC validated the part that was never in doubt and deferred the part that sinks real ERPs.

### 2. Incoherent consistency posture

The design holds three positions simultaneously: cost is provisional (fix it later), **quantity is strict** (reject oversell synchronously, under lock), and execution order across chunks is unordered (spurious drops accepted). These don't compose. The strict qty check is the *only* reason the hot path needs to read state under `pool_lock` at all — and it's enforced against a number the design elsewhere admits can be wrong-ordered across chunks. So you pay full per-pool serialization to enforce an invariant you don't actually deliver deterministically, in service of a philosophy ("record now, reconcile later") that argues against enforcing it at all. Pick a posture:

- **Everything strict** → you're back to Path A/B and per-pool ordering, honestly.
- **Everything provisional** → qty is also just a running signal, negative allowed, oversell is a recalc finding. Then the hot path needs *no read* — and that changes everything (see alternative C).

The half-measure gets the costs of both and the guarantees of neither.

### 3. The shmem queue is wrong-layer engineering

§6.2–§6.5 rebuilds, inside postmaster shared memory, exactly the machinery a durable queue provides — state machines, claims, generations, pid liveness, boot sweeps, eject/backpressure protocols, xid triage against clog — and ends up with *weaker* semantics: volatile on crash, non-transactional with the caller (savepoint hole), invisible to SQL tooling, and requiring the caller to run an outbox anyway. Meanwhile the database underneath it already has a durable, transactional, ordered, crash-recoverable queue: a table. The entire pg_xact_status/eject apparatus exists solely because the enqueue escaped the caller's transaction; put the enqueue *in* the transaction and the whole problem class evaporates — atomicity with the business write is free, WAL is the recovery protocol, the row is the observability. The shmem design optimizes enqueue latency (a shmem push vs. a heap insert), but the caller is already paying a tx + fsync for its business writes; one more insert rides along nearly free. My strong suspicion is the measured delta between shmem staging and table staging is small, because committer-side PG work dominates — and that suspicion is testable in a day (alternative A).

There's also a lifecycle cost nobody priced: a distributed system living in extension shmem means every upgrade is a postmaster restart, every shmem-layout change is a flag day, debugging is gdb-against-postgres, and none of it survives to a replica.

### 4. The RMW-across-SPI shape inflates the critical section it's trying to minimize

Even for the "constant-time" aggregate update, the flow is: acquire pool_lock row → SELECT aggregate → round-trip into ledger-core → plan → UPSERT back. The lock is held across multiple SPI calls and a Rust round-trip because the arithmetic lives outside SQL. The aggregate mutation is *almost commutative* — `qty += ΔQ, value_sum += ΔV` — and PostgreSQL will serialize a single-row `UPDATE ... SET qty = qty + $1, value_sum = value_sum + $2 WHERE pool_id = $3 AND qty + $1 >= 0` on its own row lock with a hold time of one tuple update, no `pool_lock` table, no sorted acquisition protocol, no lazy-create dance. The running-average read for a depletion fits in the same statement via a CTE. The design never asks whether ledger-core-in-Rust actually beats one SQL statement for the aggregate path; the entire pool_lock edifice (and its WAL churn, and the deadlock-ordering discipline) may be solving a problem the shape created.

### 5. The per-pool ceiling is intrinsic and unacknowledged

Every variant that maintains synchronous per-pool state — direct, batched, routed — has a hard throughput ceiling per hot pool: one serialized fold. Routed raises the ceiling to `batch_size_max / commit_time` but the ceiling remains, three committers idle behind it. The only architecture that removes it is one where the hot path doesn't read-modify per-pool state at all. The doc frames routed as *the* answer to "1000 callers, one pool"; it's actually a constant-factor improvement on a fundamentally serial design.

## Alternatives worth exploring

**A. Staging-table outbox + `SKIP LOCKED` committers (replaces §6 wholesale).** `INSERT INTO ledger_inbox` inside the caller's tx; committer loop does `SELECT ... FOR UPDATE SKIP LOCKED ORDER BY id LIMIT N`, groups by pool, processes, marks done. You get: atomicity with the caller (kills the xid triage, eject, savepoint, and syncoff problems in one move), durability, per-pool FIFO by construction (kills the spurious-drop problem), free observability (the row *is* the status; poison is an UPDATE not a shmem flag), recovery = nothing (WAL). Costs: one heap insert + drain reads + vacuum on the inbox. This is the boring design the shmem stack should have been benchmarked against before being built. It should be spike #1 — if it's within, say, 20% of shmem routed on the hot-pool scenarios, the routed crate is deletable.

**B. Single-statement commutative aggregate update (replaces §5's locking discipline).** Per problem 4: fold hydrate/plan/write for the aggregate-only paths into one SQL statement under PG's own row lock. Drops `pool_lock`, the sorted-acquisition protocol, and most of the deadlock surface for single-pool trxs. Keep ledger-core for the genuinely stateful methods (specific, future strict). Cheap spike, directly measurable against the current lock-hold numbers.

**C. Cost-less hot path: split the quantity ledger from costing entirely.** The logical endpoint of "provisional": the hot path records *only* the physical event — append trx/trx_line with qty and observed cost, touch nothing else, or at most fire a commutative delta per B. No qty gate (negative allowed, flagged), no running average maintenance, no provisional posting amounts. Costing — *all* of it, not just FIFO fidelity — becomes a batch process that assigns costs and posts GL in one pass. This is the SAP material-ledger shape taken seriously: real-time perpetual quantity, periodic valuation. It removes the per-pool ceiling (hot path is insert-only, scales with heap insert throughput), removes the provisional-vs-authoritative dual bookkeeping (there's only one costing pass, so no cost-adjustment storm), and makes recalc the *primary* costing engine you build once rather than a corrective layered on a second one. The price: mid-period GL is qty-only or standard-valued, which the business may or may not accept — but that's the question to ask *before* building two costing planes.

**D. Logical decoding as the recalc feed.** Whatever recalc gets built, don't feed it by scanning trx_line with watermarks — §14.6 already documents why allocation-order watermarks are broken. A logical replication slot delivers trx_line inserts in **commit order** with a durable cursor (`confirmed_flush_lsn`) for free. That's the safe-watermark problem solved by the substrate instead of by settled-state columns.

**E. Move the router/committer to an application-tier partitioned consumer.** Same single-writer-per-pool idea, but as an ordinary service: pools sharded across worker processes (consistent hash or a Kafka-partition-style assignment), each worker batching its pools' events into ordinary PG transactions. Identical batching math, ordinary deployment/upgrade/debugging, horizontal scale-out, and PG returns to being storage. The shmem design is this pattern implanted into the postmaster; the implantation bought enqueue latency and paid for it in everything else.

**F. Revisit the TigerBeetle split you already designed.** Your earlier ledger design had TB as the hot quantity/value plane with PG for catalog and projections — TB's native batching (8k transfers/commit, single-writer core) *is* the routed committer, built by people who did nothing else for years, with the debit/credit invariants enforced in the engine. Path C inside pgrx is, from one angle, a reimplementation of TB's write path with weaker guarantees to avoid operating a second database. That tradeoff might still be right — but it should be an explicit comparison in the doc, given the prior art is your own.

**G. Interrogate the FIFO requirement itself.** The costliest requirement in the system is per-depletion FIFO fidelity. Most regimes that "require FIFO" actually require *periodic* FIFO (month-end layer consumption), and many businesses on FIFO would pass an audit on WAC. If the answer is periodic, alternative C is the design and strict per-depletion layer math never needs to exist. If some pools genuinely need real-time layer costs (specific-id already does), scope strict mode to those pools only. The cheapest architecture is the one where the hard requirement turns out not to exist.

## What I'd actually do

Spike A and B first — both are days, not weeks, and both attack the same question: *is the custom machinery buying anything over what PG gives you natively?* If staging-table routed and single-statement direct land within noise of the shmem/pgrx numbers, most of the v3.1 codebase is complexity without yield, and that's the finding. In parallel, force the C/G conversation with whoever owns the accounting requirement, because it determines whether recalc is a corrective sidecar (hard, risky, dual-bookkeeping) or the sole costing engine (simpler, single-plane). And whatever survives, D — commit-ordered feed via logical decoding — should be a fixed decision before any recalc design starts, because it deletes the watermark problem rather than solving it.

The meta-observation: Path C's genuine insight — decouple recording from valuation — is sound. The current architecture applies it halfway (cost yes, qty no, ordering sort-of) and spends its complexity budget on a bespoke queue in the wrong layer. Applied fully, the same insight yields a simpler system with a higher ceiling.
