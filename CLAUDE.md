## Implementation stack

- **Language:** Rust.
- **Postgres driver:** `sqlx` (raw SQL, compile-time query checking against the live schema).
- **Migrations:** `sqlx-cli` — plain `.sql` files under `db/migrations/`, run via `sqlx migrate run`.
- **Tests:** `cargo test` — Rust integration tests using `tokio` + `sqlx`. **No pgTAP, no Python harnesses.** A small `tests/common/` module will provide helpers (reset to fixture, expect SQLSTATE).
- **Database:** Postgres 18 with `io_method=io_uring`, `pg_stat_statements`, `pg_cron`. Runs in Docker (host port `5111`, container port `5432`). Volume mounted at `/var/lib/postgresql` (PG 18+ convention). `seccomp:unconfined` on the dev container to allow io_uring syscalls; production hardening tracked as `acct-hbp`.

## What the project is

An ERP ledger and inventory system: SKU × location quantity tracking, per-routing-step WIP, document lifecycle (WO/SO/TO/PO), double-entry GL, multi-currency, reservations, commodity provisional pricing, period close. The design has gone through one full review cycle and has converged on a **Postgres-native v0.2** target (consolidated doc Part IV) — explicitly not a TigerBeetle drop-in or hybrid system.

## Load-bearing design decisions (do not re-litigate without cause)

These are decisions the consolidated doc commits to. If a task touches one of them, treat it as a design change requiring deliberate justification, not an incidental edit.

- **Postgres-native, no TigerBeetle parity.** The TB-parity tax (Part III) is the reason v0.2 exists. Reintroducing `NUMERIC(39)` IDs, `user_data_*` polymorphism, bit-field `flags`, the pending/post/void primitive, lazy account materialization, or AMQP CDC is a regression.
- **Reservations are first-class rows, not pending transfers.** `inventory_reservations` table with a status enum (Part IV §1.3, §3.3). The self-pending pattern from v0.1 is a documented blocker (B1).
- **Transfers are append-only.** Trigger-blocked UPDATE/DELETE on `transfers` (Part IV §1.9). Reversals are new transfers, not edits.
- **Period lock is a schema invariant, not API discipline.** `post_transfers` consults `periods.closed_at` (Part IV §2.1, §6).
- **Period close is orchestrated, not a manual `UPDATE`.** `close_period(p_period_id, p_actor, p_force_provisional, p_force_recon)` (migration 0026, `acct-s6n`) runs hooks, gates, then stamps `closed_at`. Two gates: P0015 (un-finalized `transfers_provisional` rows) and P0016 (recon alerts), each force-flag-bypassable independently. P0014 covers missing/already-closed (and concurrent-caller serialization via `FOR UPDATE` on the period row). As of `acct-og1` (migration 0032) **all three close hooks have real bodies**: `wac_periodic_close_hook` (from `acct-qfj`, migration 0029), `wac_retroactive_close_hook` (from `acct-9tw`, migration 0031), `cost_adjust_retroactive_hook` (from `acct-og1`, migration 0032). All three share the signature `(p_period_id BIGINT, p_force_provisional BOOLEAN DEFAULT FALSE) RETURNS BIGINT`. wac_retroactive uses chronological replay ordered by `(business_date, posted_at, id)` per pool; WIP class deferred under `acct-p7v` (Phase 2 Epic J). `p_actor` is unvalidated — RBAC = Part VII Q6, still open.
- **`wac_periodic` depletions post at the running pool average and are flagged in `transfers_provisional`** (acct-qfj, migration 0029). Mid-period dispatcher math is identical to wac_perpetual (`amount = qty × pool_value/per_class_qty`); the difference is the value-leg transfer is also INSERTed into `transfers_provisional` with `cost_method='wac_periodic'`. At period close, `wac_periodic_close_hook` recomputes `final_avg = Σ(in-period receipts value) / Σ(in-period receipts qty)` per `(sku, location, currency)` pool (Oracle PAC convention) and posts variance routed through `variance_wac_period`. Receipts on wac_periodic SKUs do **not** flag — they post at their actual asserted cost (po_unit_price, etc.). Empty-pool-on-depletion = P0006 (no negative inventory; tracked as Epic H `acct-9ij`). Zero-receipts-in-period at close = **P0020** (`wac_periodic_close_no_receipts`); bypassable with `p_force_provisional=TRUE`. Alternate provisional cost sources (last period close avg, last purchase price, configured value, zero, standard) deferred to Phase 2 Epic I (`acct-cms`).
- **Retroactive cost adjustment is queue-then-flush-at-close, method-agnostic** (acct-og1, migration 0032). `post_cost_adjustment_retroactive(p_target_period_id, ...)` queues a row in `inventory_cost_adjustments_retroactive`; `cost_adjust_retroactive_hook` flushes at close, posting variance through `variance_cost_adjust_retro` per non-zero-variance in-period depletion. Distinct from §3.12 `post_cost_adjustment` which is live-pool, wac_perpetual-only. Restricted to currently-open target periods (closed → **P0021** referencing `acct-7h4` Phase 2 Epic K period reopen workflow). With `wac_periodic`/`wac_retroactive` the documented behavior is double-correction (their hooks run first; cost_adjust_retroactive layers on top against the original depletion's `amount/qty`). WIP class deferred (P0006 ref `acct-p7v`).
- **Read-then-write under `FOR UPDATE` is allowed and used for cost computation.** WIP unit cost, WAC. (Part IV §3.4, §4.2.) The TB-era prohibition is dropped deliberately.
- **Per-ledger double-entry invariant.** `GROUP BY ledger_kind, currency` — never a single global sum (B3 fix; Part IV §7).
- **`BIGINT` for amounts and balances; `BIGSERIAL` for account/transfer IDs; `UUID` only for document IDs and `idempotency_key`.** Type choices are deliberate; Part IV §1.
- **Tiered read model.** Tier 1 (base tables) → Tier 2 (trigger-maintained mat views, only when measured) → Tier 3 (logical replication for OLAP/search, only when justified). Do not propose an async projector service for MVP.
- **Sync `post_transfers` for now; pivot to pseudo-sync (shape L) deferred to Phase 1+** (Part VII Q3 originally resolved 2026-04-27 as `acct-93b.3`; re-examined and re-resolved 2026-04-30 as `acct-0oy`). `post_transfers` is called synchronously inside the same Postgres transaction as document writes. The five outbox variants (G/J/K/L/M, perf_baseline_v0.md) characterize the alternatives; shape **L** (pseudo-sync via LISTEN/NOTIFY, `acct-yjn`) is the documented escape hatch. **L's latency-and-throughput-under-contention advantages are real and wanted** — caller p99 547 ms vs F's 8.25 s (15× better) is robust under noise; throughput median is ~1.8× F (the original "16 % above shape B" claim was at the high end of L's noise distribution and didn't survive `acct-ezm`'s short-run re-measurement). The deferral is **operational, not architectural**: every Phase 0 test and every Phase 1 fixture would need rewriting around an async-listener-rendezvous call site, and realistic Phase 1 workflows (per-document transfers, naturally spread across SKUs/locations) don't hit the high-contention regime where L's advantages are load-bearing. We commit to revisiting once Phase 1 produces measured contention — tracked as `acct-c4p`. The infrastructure for L (DrainConfig.notify_channel, single-listener dispatcher, drain-tx pg_notify with SQLSTATE payload) is already built and benched; pivoting later is additive, not a foundation rewrite.

- **Per-event qty is persisted on `transfers.qty`** (acct-75z, migration 0030; forward-only). Populated at INSERT time for inventory-touching events; NULL for cash/AR/AP/FX. WAC math (`wac_perpetual` and `wac_periodic`) reads its qty divisor as `SUM(transfers.qty signed by debit/credit on the value pool)` — class-isolated. Pre-0030 used `stock_available.balance` which pooled raw and fg qty for the same `(sku, location)`, breaking per-class avgs when a SKU had both pools active. `_post_transfers_lookup_qty_account` is retained for `post_transfers`'s lock pre-scan only. The "single inventory class per SKU" assumption is retired.
- **Standard cost is a separate transactional entity, not a column on `skus`** (acct-hlr, migrations 0027-0028). `skus.standard_cost` does not exist. Standard cost lives in the append-only `standard_costs` table (`sku_id`, `cost`, `effective_at`, `posted_by`, ...). The single canonical lookup is `resolve_standard_cost_at(p_sku_id, p_business_date) RETURNS BIGINT`, which raises **P0018** if no standard is in effect at `business_date`. Cost-relevant operations on standard SKUs go through this helper — the gate composes (currently catches `_post_transfers_compute_amount` standard branch + `post_inventory_adjustment` standard branch; future PO receipt / SO ship / op_move / scrap / wo_complete inherit it). Establishing or rolling the cost goes through `post_standard_cost_roll()` (INSERT into `standard_costs` + revalue raw + fg pools + audit row). WIP pools are excluded from revaluation by design — companion workflow tracked as `acct-bru` (Phase 2 Epic G). Retroactive rolls blocked (P0019); optimistic concurrency via P0017.
- **TigerBeetle is a reference model, not a parity target** (Part VII Q1 resolved, 2026-04-29). TB informs behavioral correctness (atomicity, lock semantics, idempotency, append-only) but the implementation does not have to shape itself to TB's primitives. Postgres-native ergonomics win where they conflict.
- **No fixed TPS target; correctness > performance; baseline before complexity** (Part VII Q2 resolved, 2026-04-29). The project is an exploration of what's possible Postgres-native vs the v0.1 hybrid Postgres/TB design. Phase 1 schema expansion (customers, work_orders, routings, BOMs, alternate cost methods) is gated behind the baseline so regressions are detectable.
- **PO receipt accrues to `ap_unsettled`, not `ap`** — GRNI semantics (Slice A D1, 2026-05-01, acct-7mg, migrations 0034/0035). `post_po_receipt` credits `ap_unsettled` (goods received not invoiced) at receipt; `post_ap_bill` clears `ap_unsettled → ap` at bill posting. Mainstream-ERP convention; revises the design doc's original §3.1 (which was written speculatively to credit `ap` directly). Three close-out reasons: (a) compliance — AP shouldn't be credited before invoice approval, (b) makes the receipt-to-bill match auditable as a discrete transition, (c) `ap_unsettled` already existed for the §3.13 commodity provisional case so this is a natural reuse.
- **Three-way match is strict on (sku, location, qty, unit_cost)** — Slice A D3, 2026-05-01, `post_ap_bill` (migration 0035). `qty` ≤ received-not-yet-billed remainder per `po_line` (cumulative across receipts and prior bills); `unit_cost = po_line.unit_cost`; `amount = qty × unit_cost`. Mismatches raise **P0024**. Tolerance windows, over/under-receipt, and weighted-cost averaging are deferred to Phase 2 — caller-side workflows (`post_cost_adjustment`, reversal+rebook) handle discrepancies for now.
- **`post_transfers` apply step is centralized in `_post_transfers_apply_event`** — Slice A.1 Part A consolidation pass (acct-7mg, migration 0033, fold-in of acct-q43). Validation (P0001/P0002/P0003), period resolution + gate (P0004/P0005), qty resolution, balance update, transfer insert, and `transfers_provisional` flag for wac_periodic/wac_retroactive depletions all live in one helper. `post_transfers` itself is now an orchestrator: pre-scan (cost-event detection, lock pre-scan via `_post_transfers_lock_pre_scan`), single-pass for non-WAC batches, two-pass for WAC. Future dispatcher branches (`post_so_ship`, etc.) call into the same primitives.

Mainstream-ERP convention (SAP SD / NetSuite / Oracle Cloud / D365 all separate ship from invoice in their data model); revises the design doc's original §3.3 (which was written speculatively to debit `ar` directly). New error codes: P0037 (so_ship_invalid), P0038 (so_line_overshipped), P0039 (ar_payment_invalid), P0040 (customer_invoice_three_way_mismatch), P0041 (customer_invoice_invalid_line). Mig 0081 also relaxed `post_transfers`'s SKU-resolution gate to allow `so_ship`'s revenue / tax legs (no SKU on either side via `ar_unsettled` / `revenue` / `sales_tax_payable`) to pass through with caller-supplied amount; `op_move`/`scrap`/`wo_complete` still require SKU. Reservation lifecycle gained `'shipped'` state (mig 0079); `post_so_ship` flips active reservations atomically. Phase 2 follow-ups deferred: `post_ap_payment` symmetry, `post_so_allocate`, `post_customer_return`, three-way-match tolerance windows, sales-tax integration.
- **WO parents accept `cost_method ∈ {'standard', 'wac_perpetual', 'wac_periodic', 'wac_retroactive'}`** — Slice B started standard-only (acct-b82, migration 0038); wac_perpetual lifted by acct-wig (migration 0063, sub of acct-p7v); wac_periodic single-op lifted by acct-bol (migration 0064, tier 1 of acct-8in); wac_periodic multi-op lifted by acct-smn (migration 0065, tier 2); wac_retroactive lifted by acct-rso (migration 0070, tier 3) via merged value/qty-leg chronological replay. post_op_move and post_wo_complete dispatch on `parent_sku.cost_method`: standard → bom_lines std_cum (literal, per acct-6jq plan_only default); wac_* → source-WIP-pool running avg, mirroring post_scrap's accumulated_unit_cost pattern. Reasons stay `op_move_v` / `wo_complete_v` / `scrap_v` (caller-supplied amounts) — `_post_transfers_apply_event`'s flagging condition was extended (acct-bol, mig 0064) to recognize these *_v reasons for `transfers_provisional` on wac_periodic / wac_retroactive parents, so the close hook can find depletions to recompute at period close. wac_periodic_close_hook's pool_qty_in calc dispatches on pool.kind (helper `_wac_close_pool_qty_in`): inv_value_wip reads parent qty from the matching stock_wip account; raw/fg keep the per-class pattern from acct-1vr.
- **wac_periodic close hook is a topological per-pool recompute** (acct-smn, mig 0065). Builds a DAG from in-period op_move_v transfers (predecessor → successor), Kahn-sorts pools, walks in topological order. For each pool P: `corrected_value_in = SUM(t.amount + COALESCE(p.variance_amount, 0))` over debit transfers to P (LEFT JOIN on transfers_provisional via the implicit upstream cache); `qty_in = _wac_close_pool_qty_in(P)`; `final_avg = corrected_value_in / qty_in`. For each provisional row credit-side P: variance = `(final_avg − provisional_unit) × qty`. **Internal-chain op_move_v** rows record variance but DO NOT post a transfer (variance_transfer_id NULL): both source and destination inv_value_wip pools are debit-normal and typically drained at WO close, so single-leg or 2-leg routing would push them negative on signed-mixed multi-WO drift. The cumulative cost shift surfaces at LEAF depletions (wo_complete_v / scrap_v) via tier 1's single-leg pattern (variance routes between orig_debit and variance_wac_period; source WIP untouched). Raw/fg sources keep the 2-leg wash from mig 0029. Rework cycles (op_move 20→10) raise **P0036** ('wac_periodic_pool_cycle'); deferred to acct-p7v-rework follow-up. The `transfers_provisional` CHECK was relaxed in mig 0065 to permit `finalized_at NOT NULL AND variance_amount != 0 AND variance_transfer_id IS NULL` (was previously rejected); zero-variance + transfer_id and finalized + NULL variance still rejected.

- **wac_retroactive close hook is topological + per-event chronological replay with a merged value/qty stream** (acct-rso, mig 0070). Same Kahn-sorted pool walk as wac_periodic tier 2 (op_move_v / rm_issue_to_wo edges; cycles → P0036 'wac_retroactive_pool_cycle'). Within each pool P, walks transfers chronologically by (business_date, doc_chrono, document_id, sub_priority, id) where `doc_chrono = MIN(posted_at) OVER (PARTITION BY document_id)` — anchors all transfers of one wo_event under one chronological key (each post_transfers INSERT calls clock_timestamp() per transfer, so rows of the same wo_event have slightly different posted_at but identical document_id and BD). Sub_priority orders qty inflows BEFORE value events BEFORE qty outflows: 0 = qty inflow on stock_wip, 1 = value-leg either direction, 2 = qty outflow on stock_wip. This guarantees the recompute at outflow uses pool_qty BEFORE that event's paired qty-leg decrement. For inv_value_wip pools, the merged stream pairs value-leg events on the value pool with qty-leg events on the matching stock_wip account; for raw/fg pools, only value-leg events (per-class qty pattern uses each row's t.qty). Inflow value-leg gets the upstream-variance cache (`t.amount + COALESCE(p.variance_amount, 0)` filtered to `p.variance_transfer_id IS NULL`). Outflow value-leg recomputes at running avg, posts variance through `variance_wac_retroactive`. Internal-chain reasons (op_move_v / rm_issue_to_wo) record variance only — no transfer posted; cost shift propagates via cache. Leaf depletions on inv_value_wip source post single-leg variance (debit-normal pool drained, can't wash through); on raw/fg source post 2-leg wash (mig 0031 pattern preserved). Pre-period state for inv_value_wip pools resolves qty from stock_wip signed sum; for raw/fg from per-class signed sum on the value pool itself. Mixed parent/component cost methods (e.g., standard parent + wac_retroactive component) lifted in **acct-7eo** mig 0077: close hook detects mixed shape (destination's SKU cost_method ≠ wac_retroactive) and posts single-leg variance through `variance_material_mixed` against the component pool, leaving the destination WIP untouched.

- **WO routings are per-WO inline; no shared template table at MVP** — Slice B kickoff Q1, acct-b82. `wo_routings(wo_id, routing_op, op_name)` is per-WO. Reusable templates (a `routing_templates` reference table that `wo_routings` reads from at WO creation) are left for when reuse pressure proves real, not anticipated.
- **WO variance grain is residual-only at `wo_complete`** — Slice B kickoff Q3 + BOM2 extension. The MVP surfaces `wo_close_v` against `variance_wo_close` for any nonzero `inv_value_wip@op` residual at WO close. BOM2 (mig 0061) added a **pre-balance step** at final close that reconciles pool@last_op vs `parent_std × qty` BEFORE the per-output drain — making both favorable and unfavorable variance reachable under standard cost-on-WIP without hitting the debit-normal CHECK. Plus a residual sweep across all routing ops absorbs op_move integer-truncation residue. acct-69e (mig 0068) gates both pre-balance and per-op residual sweep on **solo-at-pool** (stock_wip qty == p_qty before drain, == 0 after) so interleaved multi-WO scenarios sharing parent_sku × routing_op pools do not absorb other WOs' WIP into THIS WO's variance_wo_close. The trade-off is approximate per-WO close-variance attribution when WOs share a pool: integer-truncation residue accumulates in the pool until the LAST sharing WO closes; pool-value integrity is preserved. Per-op MUV/LV/OHV (operation-level material/labor/overhead variance) is still Phase 2; `variance_muv` / `variance_lv` / `variance_ohv` enum values exist on `account_kind` for forward compatibility.
- **`op_move`'s value-leg uses `op_move_v` reason; per-output drain in `wo_complete` uses `wo_complete_v`** — both bypass the dispatcher's auto-pricing. The dispatcher's `standard` branch returns `qty × resolve_standard_cost_at(parent_sku)` which is parent's full std cost — correct at last_op (single-output) but wrong everywhere else (intermediate ops, co-product allocation shares). The functions compute amounts externally and route through reasons that aren't in the dispatcher's cost-event list, so caller-supplied amounts stand. Mirrors the `scrap` / `scrap_v` qty-leg / value-leg split.
- **BOMs are header + lines, with alternates and revisions** — BOM2 acct-jg2 (migrations 0043/0044). `bom_headers(id, parent_sku_id, alternate_no, revision_no, code, description, status, is_primary, effective_at, obsolete_at, eco_id)` separates the BOM-as-a-thing from `bom_lines(bom_id, line_no, kind, basis, applies_at_op, fire_at, scrap_pct, component_*, qty_per_parent, absorption_class_id, std_amount)`. Alternate BOMs (alternate_no) coexist for the same parent SKU; revisions (revision_no with `effective_at`/`obsolete_at`) drive time-phased selection. `work_orders.bom_id` pins a specific BOM per WO; NULL falls back to `_wo_resolve_bom_for → bom_header_at(parent, 1, business_date)` for the primary. **P0033** if multiple primaries collide or none active. The pre-BOM2 flat `boms` table and the per-line `wo_routing_burdens` are gone (mig 0062).
- **Absorption taxonomy is runtime-configurable, not a PG enum** — BOM2 acct-jg2 (mig 0042 + 0047). `absorption_classes(id, code, applied_account_kind, expense_account_kind, ...)` is the open extension point. New classes (`osp_plating`, `production_setup`, `energy_hv`, …) are plain `INSERT`s — no `ALTER TYPE`. Classes targeting `applied_account_kind='absorption_pool'` ride generic reasons `burden_apply` (per_unit) / `lot_charge_apply` (per_lot); canonical kinds `labor_applied` / `oh_applied` keep `labor_apply` / `oh_apply` regardless of basis. `_wo_apply_reason_for(class_id, basis)` maps; **P0026** on unmapped `applied_account_kind`.
- **`bom_lines.fire_at` ∈ {`wo_start`, `op_arrival`} drives scrap-aware fire timing** — BOM2 acct-jg2. `wo_start` lines fire at `post_wo_start` regardless of `applies_at_op`. `op_arrival` lines fire when their op is reached: per_lot fires once on first arrival; per_unit services fire on every arrival (per-pass labor model). **Items fire once per lifecycle** (at `wo_start` if applies_at_op = first_op, else first arrival of applies_at_op); rework moves (op_to < op_from) emit per_unit *services* only — items never re-issue (acct-jtt fix in mig 0062, otherwise raw inventory double-consumes on rework). Charges that haven't fired yet don't fire if their op is unreached: **scrap-aware safety**. Fired charges stay in the pool and absorb against survivors on partial scrap.
- **`bom_lines.scrap_pct` is planning metadata; `skus.yield_mode` selects rollup behavior** — BOM2 acct-6jq (mig 0061). Pool flow (emission, op_move) is **literal** in all cases: `qty_per_parent × p_qty × component_std`. The future BOM rollup tool reads `skus.yield_mode`: `plan_only` (default) ignores `scrap_pct` and the parent_std equals literal sum; `absorbed` inflates parent_std by `1/(1-scrap_pct/100)` per item line. The mode flag affects only the rollup tool's output and what variance shows up at wo_complete (clean unfavorable in plan_only when actual scrap fires; favorable when actual < plan in absorbed). DO NOT re-add gross-up at emission or per-op flow — both were wrong and explicitly removed in 0061.
- **Phantom assemblies expand recursively** — BOM2 acct-jg2 (mig 0050). `skus.is_phantom = TRUE` marks SKUs that exist for cost-rollup organization but have no physical inventory. `_wo_explode_bom` flattens phantom child BOMs into the parent at the parent's `applies_at_op`. 16-level depth cap; **P0032** on cycle or depth.
- **Co-products / by-products via `wo_outputs`** — BOM2 acct-jg2 (mig 0046). `wo_outputs(wo_id, output_no, output_sku_id, fg_location_id, qty, allocation_method, allocation_pct)` distributes the FG drain across multiple output SKUs at `post_wo_complete`. `allocation_method ∈ {primary, sales_value, fixed_ratio, market_price}`. `post_wo_start` auto-initializes a single-output `primary` row when empty; otherwise validates `Σ allocation_pct = 100` (**P0033**). Lot-size variance shows up in `variance_wo_close` when actual lot ≠ default — partial-scrap with fired per_lot charges leaves the charge in pool to absorb against survivors at the amortized rate.

Workflow `draft → approved | rejected`. `post_eco_approve` flips status, populates `effective_at` on tied `bom_headers`, optionally obsoletes predecessors. **P0031** on invalid state. `acct-ECO-WORKFLOW` follow-up (acct-ir7) covers the broader review/approval workflow.

- **Class-confusion checklist (acct-rgb / acct-fii / acct-69e / acct-7py / acct-69p / acct-smn / acct-rso regression lock)** — `acct-du2` codified the bug-class "function presents class-/cost-method-/document-specific semantics but reads cross-class / cross-method / cross-document state." Six rules every new function or modification touching pools/dispatch/idempotency must satisfy; each fix-needed flag from `REVIEW.md` traces back to one of these:
  - **R1** Per-class qty divisors come from per-class signed SUM on the value pool's `transfers.qty`, NEVER from `stock_available` (which is cross-class for raw + fg same-location). Motivated by **acct-fii** (post_cost_adjustment) and the sibling unfixed sites **acct-du2.8** (post_inventory_adjustment) and **acct-du2.11** (post_standard_cost_roll).
  - **R2** `cost_method` dispatch + `transfers_provisional` flagging resolve SKU from the CREDIT side (depletion source) of the transfer. Motivated by **acct-rgb** (component cost dispatch) and **acct-7py** (multi-output co-product flagging). `_post_transfers_compute_amount` debit-first COALESCE is **acct-du2.4** drift risk.
  - **R3** Functions that mutate a shared pool gate state-affecting operations on solo-occupancy: pool_qty_before == this_doc's_contribution; pool_qty_after == 0. Motivated by **acct-69e** (post_wo_complete pre-balance + residual sweep). Sibling **acct-du2.10** lifts the gate to post_wo_close_unproduced.
  - **R4** Pool reads happen under `FOR UPDATE` on the SAME account before subsequent writes — `FOR UPDATE` on the value account does NOT cover the qty account. Motivated by **acct-du2.1 / .2 / .6 / .7 / .9 / .12** (multiple lock-gap findings).
  - **R5** Variance routing on debit-normal pools that the document path drained to 0 in-period uses single-leg (orig_debit ↔ variance_acct), not 2-leg through the pool. Motivated by **acct-smn** (wac_periodic close hook on inv_value_wip).
  - **R6** Idempotency replay checks happen BOTH before `FOR UPDATE` (fast path) AND immediately after (race-safe). Motivated by **acct-69p** (post_wo_start / post_wo_complete) and the sibling unfixed sites **acct-du2.3** (post_osp_*) and **acct-du2.5** (post_op_move / post_scrap consistency).
